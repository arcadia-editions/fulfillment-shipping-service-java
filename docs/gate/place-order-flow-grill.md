## 1. Deterministic checks

- Lint: `bash .zenwave/bin/lint-zdl.sh --strict ../fulfillment-shipping-api/domain-model.zdl` -> `OK` (no errors, no
  warnings, no `zdl.data-lineage`).
- `@zdl(...)` paths: the 5 resolve (`orders-checkout-api`, `catalog-inventory-api`, `payments-processing-api`,
  `fulfillment-shipping-api`, `notifications-consumer-api`).
- Commands of `FulfillmentShipping` (zfl:30) exist in the ZDL: `scheduleFulfillment` (zdl:133),
  `recordPaymentCaptured` (zdl:140), `cancelFulfillment` (zdl:149). `markReadyToShip` (zdl:144) is in the ZDL but not
  in the flow (as designed: warehouse action, finding F-09).
- Events: `FulfillmentScheduled` (zdl:153), `FulfillmentFailed` (zdl:161), `FulfillmentCancelled` (zdl:181) exist;
  consumed `OrderConfirmed`, `OrderCancelled` (orders zdl:175, :196), `PaymentCaptured` (payments zdl:248) exist, and
  their channels (`order-confirmed-event-v1`, `order-cancelled-event-v1`, `payment-captured-event-v1`) exist in the
  producers' `asyncapi.yml`.
- `@compensates(scheduleFulfillment)` (zfl:316) names a command. `systems` entry `FulfillmentShippingService` matches
  the ZDL service.

## 2. Findings and decisions

| # | Finding (model lines) | Decision / where |
|---|---|---|
| F-01 | **Correlation**: every consumed event carries `orderId`, never `fulfillmentId` (zfl:184, :219, :317; orders zdl:175-204, payments zdl:248). `Fulfillment.orderId` is `unique` (zdl:58). | As designed: listeners correlate by `orderId` with `findByOrderId` (board T-04). |
| F-02 | **Lineage** `ScheduleFulfillmentInput` (zdl:93-98): `orderId`, `customerId`, `items`, `shippingAddress` all come from `OrderConfirmed` (orders zdl:175-193). Avro fields are nullable there; the input marks them `required`. | As designed: orders validates them at `StartOrderCheckout`; a message that fails validation goes to the retry/DLQ topics of `asyncapi-client.yml`. No test data. |
| F-03 | **Lineage** `fulfillmentId` (zdl:57) has no source upstream. | Decided T-05: UUIDv7 generated by the service (board). |
| F-04 | **Branch rule** SCHEDULED vs FAILED and `failureReason` (zfl:178-188, zdl:132-133, :79) have no source. | Decided T-06, ADR 0002: stand-in, `postalCode` `00000` -> FAILED `CARRIER_UNAVAILABLE`, else SCHEDULED. |
| F-05 | **Lineage** `RecordPaymentCapturedInput.capturedAt` (zdl:103) <- `PaymentCaptured.capturedAt` (Avro string, ISO-8601); `CancelFulfillmentInput.reason` (zdl:109) <- `OrderCancelled.reason`. | As designed: mapping in the listeners (T-11 parses the ISO string, T-14); `cancellationReason` = the reason (data.sql A-03). |
| F-06 | **Handled**: `FulfillmentScheduled` -> `capturePayment` (zfl:196), `FulfillmentFailed` -> `voidPayment` (zfl:246), `FulfillmentCancelled` published for the warehouse (zdl:179 doc), `FulfillmentReadyToShip` (zdl:170) has no consumer in any ZDL. | As designed: both are published for the (future) warehouse. No change. |
| F-07 | **Ended**: FAILED -> void -> release -> `cancelOrder` -> `OrderCancelled` -> `cancelFulfillment` no-op -> `orderCancelled` (zfl:236-320). SCHEDULED + capture failed -> ... -> `OrderCancelled` -> CANCELLED -> `orderCancelled`. SCHEDULED + captured -> `recordPaymentCaptured` (no event) while notifications ends `completed`. | As designed: every branch ends. |
| F-08 | **Compensated**: `cancelFulfillment` compensates `scheduleFulfillment` once per `OrderCancelled` (zfl:316); on FAILED it is a no-op (nothing to undo); orders emits `OrderCancelled` only once (zfl:303). | As designed (C-04, C-09, C-10, C-21 in data.sql). |
| F-09 | **Triggered**: `markReadyToShip(id)` (zdl:144) has no trigger (no `@post`, no `@asyncapi`; openapi.yml `paths: {}`) and no input for `carrierCode` / `trackingNumber` (zdl:74-75, :174-175). P-01. | Decided for the demo without a model change, P-01 `rejected` (see its Decision): the command stays a service method only (place-order-flow does not trigger it, zfl:30), carrier values are stand-ins set by the service (ADR 0002 "Ready to ship"). T-18 released. |
| F-10 | **Ordering race**: `FulfillmentScheduled` is sent by the generated producer before the transaction commits; payments may capture and `PaymentCaptured` may arrive before the Fulfillment row is visible, so `recordPaymentCaptured` is a no-op and `markReadyToShip` stays refused forever. Same window loses events on a crash after commit. | Decided: transactional outbox, ADR 0003, implemented before the AFK loop (events leave after commit). Test of it: board T-19. |
| F-11 | **Concurrency**: `markReadyToShip` and `cancelFulfillment` on the same SCHEDULED Fulfillment. | As designed: `@Version` optimistic lock (generated); the loser fails and Kafka redelivers `OrderCancelled`, which then cancels from READY_TO_SHIP (allowed, zdl:148). No test data beyond C-22. |
| F-12 | **Redelivery** (zfl:67-68): `scheduleFulfillment` for an existing `orderId`, `recordPaymentCaptured` already set, `cancelFulfillment` on CANCELLED: no-op, no event. | As designed (zdl:130, :137, :146); fixtures C-01, C-09. |
| F-13 | **Lifecycle**: `@lifecycle(initial: SCHEDULED)` (zdl:55) but `scheduleFulfillment` creates SCHEDULED or FAILED (zdl:132). FAILED and CANCELLED are terminal; READY_TO_SHIP -> CANCELLED is allowed but no path of this flow cancels after capture. | As designed: `initial` is the happy creation state; the cancel from READY_TO_SHIP is kept for the warehouse (C-22). |
| F-14 | **Ownership**: only FulfillmentShipping mutates Fulfillment; it reads no other context. | OK. |
| F-15 | **Timers**: none in this context. The 10-minute expiry (zfl:275) never reaches a confirmed order with a Fulfillment (confirmOrder rejects, zfl:155-164). | OK. No test data. |
| F-16 | **Contracts**: asyncapi.yml topics = ZDL `@asyncapi` (zdl:152, :160, :169, :180); asyncapi-client.yml operations = the three `@asyncapi` listeners. openapi.yml has no paths (F-09). | OK; projections in [place-order-flow-projections.md](place-order-flow-projections.md). |
