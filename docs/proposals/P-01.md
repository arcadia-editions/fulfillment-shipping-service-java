# P-01 markReadyToShip has no trigger and no input for carrierCode and trackingNumber

status: rejected (demo: no model change; markReadyToShip stays internal with stand-in carrier values, ADR 0002)
found by: zenwave-test-scenarios, claude opus, 2026-11-25
flow: place-order-flow
blocks: T-18 (markReadyToShip)

## Problem
The ZFL says the warehouse may mark the order ready to ship only after capture
([place-order-flow.zfl:54](../../../arcadia-editions-architecture/business-flows/place-order-flow.zfl#L54),
[:216](../../../arcadia-editions-architecture/business-flows/place-order-flow.zfl#L216)), and the ZDL has the command
([fulfillment-shipping-api/domain-model.zdl:142-144](../../../fulfillment-shipping-api/domain-model.zdl#L142)):
`markReadyToShip(id) Fulfillment withEvents FulfillmentReadyToShip`. But:

1. Nothing triggers it. It has no `@post`/`@put` inside `@rest("/fulfillments")`
   ([domain-model.zdl:127](../../../fulfillment-shipping-api/domain-model.zdl#L127)) and no `@asyncapi` listener, so
   the released [openapi.yml:37](../../../fulfillment-shipping-api/openapi.yml#L37) has `paths: {}` and the warehouse
   has no way to call it.
2. FulfillmentReadyToShip carries `carrierCode` and `trackingNumber`
   ([domain-model.zdl:170-177](../../../fulfillment-shipping-api/domain-model.zdl#L170)), stored on Fulfillment
   ([domain-model.zdl:74-75](../../../fulfillment-shipping-api/domain-model.zdl#L74)), but the command takes only `id`:
   no input carries them, and no other command sets them.

## Evidence
`FulfillmentShippingServiceImpl.markReadyToShip(Long id)` is generated with no controller; fixture C-22
(`data/jpa/Fulfillment/7.json`, READY_TO_SHIP) uses invented values `CARRIER-01` / `TRK-022` (assumption A-04 in the
`data.sql` header). A test of markReadyToShip cannot assert where those values come from.

## Options
- A: `@post("/{id}/ready-to-ship") markReadyToShip(id, MarkReadyToShipInput)` with
  `input MarkReadyToShipInput { carrierCode String required, trackingNumber String required }`. Changes: ZDL, openapi.yml
  (re-release service-all 0.2.1), generated controller and tests; fixtures unchanged.
- B: a warehouse event (e.g. `ParcelPacked { orderId, carrierCode, trackingNumber }`) consumed with `@asyncapi`. Changes:
  ZDL, a warehouse contract that doesn't exist yet, asyncapi-client.yml; fixtures unchanged.
- C: keep `markReadyToShip(id)` internal, add the endpoint only, and drop carrierCode/trackingNumber from the entity and
  FulfillmentReadyToShip. Changes: ZDL, asyncapi.yml (breaking for consumers of the event), C-22 fixture.

Recommendation: A, the ZDL already says it is a warehouse action and the event already has the carrier fields.

## Decision
2026-11-26, claude on behalf of the person (gate review delegated; demo: "it should run, do not overcomplicate").
Rejected for the demo: no option A/B/C, no model change, no re-release. Why: place-order-flow does not trigger
markReadyToShip (zfl:30 lists only scheduleFulfillment, recordPaymentCaptured, cancelFulfillment) and there is no
warehouse system to call it; the modulith does the same (service method only).

- markReadyToShip(id) stays a service command with no inbound adapter (no controller, no listener); tests call it.
- carrierCode = `STAND-IN`, trackingNumber = `TRK-` + fulfillmentId, set by the service when it moves to
  READY_TO_SHIP (ADR 0002, "Ready to ship"). The C-22 fixture uses those values (`STAND-IN` / `TRK-FUL-022`, data.sql A-04).
- Board: T-18 released (`blocked: P-01` removed). A real warehouse trigger is option A or B in a later flow.
